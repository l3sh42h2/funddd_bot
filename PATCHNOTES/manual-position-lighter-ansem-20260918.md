## Что это и что НЕ это

Read-only витрина в /cabinet. НЕ пишет в trade.db, НЕ проходит через торговое ядро/coordinator/generic-adapter
механизм (`store.create_generic_deal`) — это позиция, открытая владельцем вручную через интерфейс биржи/DEX, а не
ботом; семантика trade.db (restart_check, reconciliation, «чья это позиция и кто её закрывает») рассчитана на то,
что каждая сделка была открыта ботом, и здесь не подходит. Сеть — только в разовом прогоне `funding_bot manual-poll`
(крон/таймер раз в минуту), НЕ внутри обработки HTTP-запроса кабинета и НЕ внутри core (core сети не делает).

## Архитектура (три новых куска, по образцу уже существующего table.json/collector)

1. `runtime/manual_positions.toml` (НЕ в git — репозиторий публичный, адреса кошельков туда не кладём; пример —
   `deploy/manual_positions.toml.example`) — факты, которые вводит владелец/оператор: id, монета, дата входа,
   заметка, адрес Lighter-аккаунта (EVM) + символ рынка, кошелёк/mint Solana (только для отображения).
2. `src/funding_bot/manual_positions.py` (новый модуль) — `poll_lighter_account()`: один публичный GET
   `/api/v1/account?by=l1_address` (без ключей, без подписи) → сторона/размер/марк/`total_funding_paid_out`
   (это и есть «фандос» — счётчик самого Lighter, не наш расчёт). `poll_once()` пишет результат в
   `runtime/manual_positions_live.json` тем же `atomic_json`, что коллектор пишет table.json. `deal_views()`
   читает ОБА файла (без сети) и собирает карточки для /cabinet; пустой/битый/отсутствующий файл → `[]`, страница
   не падает.
3. `funding_bot manual-poll` (новая CLI-команда, `cli.py`) — разовый прогон `poll_once()`, вызывается крон/таймером.

`cabinet.py`: `Cabinet.snapshot()` зовёт новый инжектируемый `manual_positions_loader` (по умолчанию
`manual_positions.deal_views`, как и `snapshot_loader` уже был инжектируемым) и приплюсовывает карточки к списку
сделок ядра — единственная точка сшивки, ядро/IPC/`interface/projections.py` не тронуты вообще. Исключение любое
из `manual_positions_loader` — перехватывается и логируется, страница отдаёт то, что было (см. тест
`test_manual_positions_loader_exception_does_not_crash_page`).

Новая карточка (`manual_deal_card`) — отдельная функция, не встроена в существующую ветвистую `deal_card`/
`pnl_block`/`live_cells`/`history_block` (та рассчитана на данные из trade.db с проверенной полнотой потоков):
чип «✋ Ручной вход», две ноги текстом (перп: площадка/адрес/сторона/размер/марк; спот: площадка/кошелёк/mint —
адреса усечены как и mint у обычной SOL×HL связки), «PnL: нет подтверждённой оценки (cost basis спота не
отслеживается)» — честно, без притворства, что PnL посчитан, большая цифра «фандинг с входа (счётчик Lighter)»
в стиле существующих PnL-цифр (`_pnl_usd`), ошибка опроса или «устарело» (>5 мин без свежего опроса), заметка.
`summary_text()` считает ручные позиции отдельной строкой («ручных N»), не смешивая с «сделок N» бота.

## Ограничения и открытые вопросы владельцу

- Поддержана только перп-нога на Lighter (единственная площадка с публичным account-API без ключей и без подписи).
- Спот-нога (Solana) показывается только как факт (кошелёк/mint из конфига) — баланс/статус двух лимитников
  Jupiter не опрашивается в этой версии (не требовалось «считает фандос» — это была бы отдельная, более сложная
  задача: публичный API Jupiter Trigger Orders для этого кошелька вернул пустой список при проверке 18.09,
  расхождение с реальностью не объяснено).
- Крон/таймер для `funding_bot manual-poll` НЕ установлен этим изменением (только код+CLI) — установка на VPS и
  сам `runtime/manual_positions.toml` с реальными адресами — отдельный шаг после ревью, я сделаю это по команде
  владельца при выкате.

## Независимая проверка 18.09 (sonnet-max) и фиксы

Реальный P1 (проверено против ЖИВОГО API Lighter, не только против схемы): `position` в ответе — величина БЕЗ
ЗНАКА, сторона — отдельное поле `sign` (-1 шорт, 1 лонг; подтверждено и схемой официального `lighter-python`).
Первая версия угадывала сторону по знаку `position`, которого там нет, — на реальном аккаунте владельца шорт
показался бы в кабинете «лонг». Тест был написан под то же неверное предположение (мок с `"position": "-…"`),
поэтому не поймал. Исправлено: `poll_lighter_account()` берёт сторону только из `sign`; тест-фикстура и 5 новых
тестов — по реальной форме ответа (`sign` + величина без знака), включая явную регрессию на «`position` со знаком,
`sign` главнее».

Также по находкам ревью: (P2) ручные карточки больше не прячутся вместе с сообщением об ошибке ядра
(`deals_fragment` в cabinet.py) — недоступность/протухший снимок core (`core_not_ready`/`projection_stale`, рутинно
при рестарте) больше не скрывает позицию, которая от ядра и не зависит; (P2) `funding_bot manual-poll` возвращает
1, если хоть одна позиция с ошибкой (как `audit` в cli.py — раньше всегда 0, крон не увидел бы затянувшийся сбой);
(P3) `poll_lighter_account` не падает на валидном-но-странном JSON (`accounts` не список словарей, `null` внутри
`positions`); (P3) убрано несуществующее в реальном API поле `mark_price` (реально есть только `avg_entry_price` —
раньше `or` всегда проваливался в него молча, поведение не менялось, но название поля вводило в заблуждение).
Не менялось: сетевая/парсинг-ошибка → `{"error": …}`, HTML-экранирование, atomic_json/Decimal↔str — ревью
подтвердило, что здесь всё было верно с первого раза.

Тесты после фиксов: 35 в новых двух файлах (было 28), полный набор — 3046 passed, 4 skipped, тот же 1
known-unrelated fail (lock-файл).
