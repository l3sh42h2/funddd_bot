## FINAL-01 · P1 — callback отправки ACK'ал чужое событие (позднее связывание в Python-замыкании)

### Проблема

`src/funding_bot/interface/runtime.py: Interface.deliver_once()`, ветка `elif kind == 'send':`:

```python
def on_sent(res, iid=track_iid):
    if iid is not None:
        ...
        self.sender.edit(chat_id, message_id, text, html=True, throttle=True)
    done(res)
```

`iid` был закреплён default-аргументом верно, но `done` — свободная переменная: `on_sent` не берёт
её параметром, а `done` — функция, заново определяемая на каждой итерации `for ev in events:` (та же
функция чуть выше в теле цикла, `def done(res, eid=eid): ...`, с ЕЁ СОБСТВЕННЫМ корректным закреплением
`eid`). `tg/sender.py: Sender` всегда зовёт `on_done` асинхронно — из потока отправителя, после того как
вызывающий код (весь `for`-цикл `deliver_once()`) уже отработал и `done` в его локальной области успела
переопределиться на ПОСЛЕДНЕЕ значение. Python резолвит свободную переменную `done` внутри `on_sent` по
позднему связыванию — на момент ВЫЗОВА, а не на момент создания замыкания — поэтому к моменту, когда
Sender реально зовёт `on_sent` для события 1, `done` в его замыкании уже указывает на `done` события 2
(или последнего в батче). Результат: ACK от события 1 приходит с `eid` события 2 (или наоборот, в
зависимости от того, какая отправка резолвится последней) — доставленное сообщение подтверждает чужое
уведомление, включая привязку `message_id` к чужому плану (`intents.msg_id` через
`Journal.acknowledge`), а действительный получатель этого ACK остаётся в `Interface.inflight` навсегда
(до перезапуска процесса) и никогда не перечитывается заново.

Касается ВСЕХ `kind == 'send'` уведомлений, не только progress/sol_progress — это самый частый путь
доставки (обычные сообщения, тревоги, финальные отчёты, подтверждение плана входа/выхода).

### Исправление (`src/funding_bot/interface/runtime.py`)

1. Закрепить `done` default-аргументом ровно как `iid`: `def on_sent(res, iid=track_iid, done=done):`.
   Default-аргумент вычисляется один раз при СОЗДАНИИ функции (на этой итерации цикла), а не при
   вызове — значит `on_sent` навсегда получает СВОЮ, а не последнюю, `done`.
2. Обёрнут вызов `self.progress.resolved(...)`/`self.sender.edit(...)` (доставка накопленного
   pending-прогресса — необязательная, best-effort часть) в `try/except`: если она бросит исключение,
   `done(res)` для ОСНОВНОГО события (успешно отправленного или нет) всё равно вызывается следом, вне
   try — иначе первое, реально доставленное сообщение тоже теряло бы ACK из-за сбоя ВТОРИЧНОЙ операции.
   Исключение логируется (`log.error(..., exc_info=True)`), не поглощается молча.
3. `self.inflight`/`self.inflight_lock`: после фикса `done`, используемая внутри `on_sent`, — это
   ВСЕГДА `done` СВОЕЙ итерации, а значит её собственный `eid=eid` default-аргумент тоже всегда верный
   (он и раньше был закреплён корректно — путал именно выбор МЕЖДУ разными `done`, не значение `eid`
   внутри правильно выбранной). Отдельно перепроверено новыми тестами (ниже): `ui.inflight` после
   успешного батча пуст, после неуспеха — содержит только реально недоставленный `eid`.

## FINAL-02 · P2 — throttle-коалесцирование в Sender теряло callbacks вытесненных задач

### Проблема

`src/funding_bot/tg/sender.py: Sender.edit()`:

```python
with self._lock:
    if throttle:
        self._edits[key] = job          # заменяет job целиком, включая on_done предыдущей
        return True
    self._edits.pop(key, None)          # обычная правка тоже молча выкидывает ждущую throttled-job
return self._put(job)
```

`_flush_edits()`/`_deliver()` доставляли только последнюю `job` по каждому ключу `(chat_id,
message_id)` и звали только её `on_done` — `on_done` job'ов, вытесненных при коалесцировании
(throttle→throttle ИЛИ throttle→нетrottle, когда обычная правка — например, закрытие плана —
вытесняет ждущий прогресс), терялся навсегда. Соответствующий durable-событие в core оставался
неподтверждённым и застревал в `Interface.inflight`, хотя текст, который его вытеснил, реально
доставлялся в Telegram.

### Исправление (`src/funding_bot/tg/sender.py`)

1. Новое поле `Sender._edit_waiters: dict[(chat_id, message_id), list[on_done]]`.
2. `Sender.edit()`: перед заменой/удалением job'а по ключу (throttle=True перезаписывает, throttle=False
   вытесняет ждущую throttled) читает, что было по этому ключу ДО изменения (`superseded`); если у
   вытесненной job был `on_done`, кладёт его в `_edit_waiters[key]` — список растёт при каждой
   последующей замене того же ключа, ничего не теряя даже при N подряд коалесцированных правках.
3. `Sender._deliver()`: после доставки (успешной или нет) job'а `kind == "edit"` — забирает и очищает
   `_edit_waiters.pop((chat_id, message_id), ())`, вызывает КАЖДОГО собранного waiter'а, а также
   собственный `job.on_done`, ОДНИМ И ТЕМ ЖЕ результатом: успех → все получают тот же
   `{'message_id': ...}` реально доставленного сообщения; неуспех → все получают `None` — то же
   значение, с которым `Interface.deliver_once()`'s `done(None)` не подтверждает событие и просто
   снимает его с `inflight`, оставляя недоставленным для естественного повтора на следующем
   `deliver_once()`. Ни один вытесненный waiter не объявляется «доставленным» тихо, и ни у одного
   нет своей отдельной retry-семантики — все ведут себя как их собственное отдельное недоставленное
   уведомление, просто с тем же физическим результатом, что и job, которая реально ушла в Telegram.
4. Каждый callback вызывается в своём собственном `try/except` (как и раньше для одиночного
   `job.on_done`) — падение одного waiter'а не мешает остальным получить свой результат.
5. Обычные (не throttled) правки не затронуты: `superseded` при `throttle=False` равен `None` почти
   всегда (кроме случая, когда он вытесняет ждущую throttled-правку — п.2 выше), значит
   `_edit_waiters` для их ключа остаётся пустым, и `_deliver()` просто зовёт их собственный `on_done`
   как раньше (`test_unthrottled_edits_to_same_key_still_deliver_and_ack_independently` — контроль).

   `deliver_once()` САМ перечитывает и передиспатчит ещё недоставленное событие, это и проверяется);
   план (`plan_id`, реальные `Journal`+`intents`) рядом с обычным сообщением не получает чужой

   best-effort правки внутри `on_sent` не стоит основной отправке её ACK.
2. **FINAL-02** (real Sender + FakeSession, 5 тестов): throttle-коалесцирование двух и трёх правок

   следующего flush Sender'а — итог совпадает с ожиданием ревью буквально:
   `{1: {'message_id': 77}, 2: {'message_id': 77}}`, `inflight` пуст.
