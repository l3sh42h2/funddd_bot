# M4: progress/sol_progress снова правят одно сообщение вместо спама новыми

Date: 2026-09-16
Author: Claude

Ref: независимое ревью AC-07 (коммит `4993f76`, `codex/migration-m4-m5`) нашло, что после переноса
`progress`/`sol_progress` на общий DTO-путь (`hooks.notice` → `Bot.execution_notice` → `Outbox` →
`interface/presenter.py: present()`) каждая стадия исполнения шла НОВЫМ Telegram-сообщением вместо правки
одного — `present()` для `kind=='execution_notice'` безусловно возвращал `kind='send'`, без ветвления по
`topic`, а `kind='send'` в `interface/runtime.py: Interface.deliver_once()` всегда шлёт новое сообщение.
Codex подтвердил находку и явно оставил вопрос владельцу: «это не денежный риск, но нужно решить, возвращаем
ли edit-in-place». Владелец поручил исправить, не просто задокументировать.

## Что было раньше (для сравнения, не выдумано)

Механизм editin-place существовал дважды в этом кодовом дереве, оба раза — простой `dict` в памяти,
ключ `intent_id`:

- **`core/commands.py` / `tg/bot.py`: `Bot._progress`/`Bot._progress_pending`** — старый throttle-путь
  (`Bot.progress(iid, html)`): первая стадия — новое сообщение, дальше — правка не чаще `TG_EDIT_MIN_S`;
  пока id первого сообщения ещё «в пути» (`self._progress[iid] is None`), следующая стадия не шлёт ничего
  нового — только запоминает последний текст (`_progress_pending`), и он уходит правкой, как только придёт id.
  **Этот путь и сейчас жив — но только в `tg/bot.py`** (однопроцессный `funding_bot trader`): его
  `BotHooks.notice()` явно проверяет `if topic in ('progress', 'sol_progress'): self.bot.progress(facts['intent_id'], text)`
  и вызывает старый throttle-механизм. В `core/commands.py: BotHooks.notice()` (трёхпроцессный режим) этой
  ветки нет — она безусловно идёт в `self.bot.execution_notice(topic, facts)` → DTO. Миграция AC-07 перенесла
  рендер из core в interface, но не перенесла это ветвление вместе с ним — вот и весь баг. Однопроцессный
  режим (`tg/bot.py`) этим багом не затронут вообще, я его не трогал.
- **`core/journal.py`: `Outbox.plan_proposed`/`plan_closed``** — другой пример того же приёма (routing-ключ
  рядом с непрозрачным DTO, не внутри него): `plan_id` кладётся в сам payload `send`, `Journal.acknowledge`
  берёт `payload.get('plan_id')` без декодирования фактов и пишет `message_id` плана в `intents.msg_id` —
  но это **живёт в core** и **персистентно** (план можно одобрить после рестарта, значит id должен пережить
  его). Я рассматривал этот путь как образец для progress и отверг его — см. «Архитектурное решение» ниже.

## Архитектурное решение: map живёт в `interface`, не в `core`

`intent_id -> message_id` хранится в новом `interface/progress_tracker.py: ProgressTracker` — объекте,
которым владеет `interface.runtime.Interface` (`self.progress`, один на процесс). `core` не меняется вообще:
`trade/engine.py`/`trade/sol_flow.py` как звали `hooks.notice('progress'/'sol_progress', facts)` с
`intent_id` внутри `facts`, так и зовут; `core/journal.py: Outbox.execution_notice` как кодировал и клал DTO
в `core_notifications`, так и кладёт — байт в байт тот же DTO, та же версия (`EXECUTION_NOTICE_VERSION=5`,
`EXECUTION_NOTICE_FIELDS` не менялись).

Почему не в `core`, хотя `Outbox.plan_proposed`/`plan_closed` — прецедент именно там: `message_id` — деталь
транспорта Telegram, а границу «core не знает про Telegram» AC-07 только что провёл явно
(`PATCHNOTES/m4-ac07-full-core-interface-boundary-20260916.md`). Чтобы `core` знал `message_id` progress-
сообщения, пришлось бы заново провести его через `ack_notification`/`Journal.acknowledge` (как это уже
сделано для `plan_id`) и завести для него персистентное место — по сути, воспроизвести design `plan_proposed`.
Это лишняя сложность без выгоды: у progress, в отличие от плана,

- никто не действует по message_id после рестарта (план можно одобрить кнопкой спустя часы — прогресс
  никто не «одобряет»; следующая стадия либо придёт от живого исполнителя, либо не придёт, потому что
  сделка уже остановилась/встала);
- ровно один процесс (`interface`) вообще вызывает Telegram API и узнаёт `message_id` — значит ровно он
  должен решать send vs edit, без похода за этим знанием в другой процесс и обратно.

Итог: `interface/presenter.py: present()` получил необязательный параметр `progress` (по умолчанию `None` —
старое поведение «всегда send» не меняется ни для одного существующего вызова, включая все тесты и
`cli.py`). Для `topic in ('progress', 'sol_progress')` `present()` зовёт `progress.route(intent_id, chat_id,
text)`:

- **не видели `intent_id`** → `kind='send'`, с меткой `progress_intent_id` в возвращаемом dict — только
  чтобы `Interface.deliver_once()` знал, куда потом отдать пришедший `message_id` (в `Outbox`-DTO этого
  поля нет и не будет — это чисто internal-marker между `present()` и `deliver_once()` внутри одного
  процесса, не часть протокола с core);
- **`intent_id` уже в полёте** (первый `send` ещё не вернул `message_id` — `Sender.send()` кладёт задание в
  очередь и возвращает управление сразу, `on_done` придёт позже из потока отправителя) → `kind='noop'`:
  текст этой стадии копится в трекере (`_pending`, последний текст вытесняет предыдущий — тот же приём, что
  документирован в `tg/sender.py` для throttled-правки: «более новый текст вытесняет ждущий»), само
  уведомление тут же ack’ается (`done({})`), чтобы не читаться заново вечно. Как только придёт
  `message_id`, `ProgressTracker.resolved()` отдаёт этот накопленный текст обратно, и `Interface` шлёт его
  ОДНОЙ throttled-правкой — а не N сообщений за то время, что Telegram отвечал на первое;
- **`message_id` известен** → `kind='edit'` с `throttle=True` (то же значение, что раньше стояло у старого
  `Bot.progress()`: `self.sender.edit(chat, mid, html, throttle=True)` — рабочая rate-limit семантика в
  `tg/sender.py: Sender.edit()`/`_flush_edits()` не переписывалась, только снова используется по назначению).

Без `wait`/`noop`-состояния (наивная версия «видели/не видели `intent_id`») была бы ровно та же дыра, что
чинится: пачка стадий, пришедших раньше, чем Telegram ответил на первый `send()`, снова дала бы N новых
сообщений вместо одного. Мутационная проверка (см. «Тесты») это отдельно подтверждает.

### Сброс состояния (п.3 задания)

`ProgressTracker.forget(intent_id)` зовётся из `present()` для топиков `halt`, `sol_halt`, `executor_crash`
(`PROGRESS_TERMINAL_TOPICS`) — они несут `intent_id` и однозначно завершают цепочку прогресса этого
намерения (пауза/крах исполнителя — та же сделка продолжится, если вообще продолжится, НОВЫМ `intent_id`
через «продолжить», `trade/store.py: create_intent` строит id заново). Проверено по коду
(`trade/engine.py: Engine.execute/_execute/_paused`, `trade/sol_flow.py: SolEngine._paused`): `halt`/
`sol_halt` шлётся ровно один раз на остановку прогона, `executor_crash` — в `except Exception` вокруг всего
`_execute(iid)`, тоже терминально для этого `iid`.

`fix_done`/`perp_closed`/`final_report` — успешный путь завершения цепочки — **не несут `intent_id`**
(`EXECUTION_NOTICE_FIELDS['fix_done'|'perp_closed']`, `final_report` — вообще отдельный DTO `kind`), поэтому
ими нельзя адресно стереть запись. Это осознанно оставлено непокрытым явным `forget()` и закрыто иначе:

1. `intent_id` **не переиспользуется** — проверено по коду: `trade/store.py: create_intent` генерирует id
   через `new_id()` и проверяет уникальность запросом по ВСЕЙ таблице `intents` (`SELECT 1 FROM intents
   WHERE id=?`), а строки из `intents` нигде не удаляются (грепом — ни одного `DELETE FROM intents`, только
   триггер `operation_intents_no_delete`, запрещающий удаление у соседней таблицы). Значит забытая запись
   `intent_id -> message_id` никогда не «подхватится» чужой более поздней сделкой — максимум эффект: одна
   лишняя запись висит в памяти впустую.
2. Рост ограничен и без точечного `forget()`: `trade/engine.py: Engine.run()` — один поток-исполнитель,
   разбирающий `self.q` строго по одному `intent_id` за раз (`self.execute(iid)` блокирует, пока не
   закончит), и `trade/store.py: approve_intent` отдельно защищён CAS через `StoreBusy` («уже идёт другое
   исполнение») — вторая параллельная цепочка прогресса физически не может начаться, пока не закончилась
   предыдущая. Значит в здоровом боте открыта максимум ОДНА запись. `ProgressTracker.max_tracked=32` — это
   просто страховка на случай, если это свойство когда-нибудь перестанет быть верным (FIFO-вытеснение
   самой старой РАЗРЕШЁННОЙ (`_message_id`) записи; сама по себе не нужна для корректности — см. `_prune_locked`).

### Рестарт `interface` (п.4 задания)

Карта **только в памяти**, не персистится — сознательно, как продолжение прецедента, а не новое решение:
старый `Bot._progress`/`_progress_pending` (и в `core/commands.py`, и в `tg/bot.py`) тоже был обычным
`dict` на процессе, без записи в БД/журнал — рестарт процесса, которому он принадлежал (раньше — `core`,
теперь по факту — только `tg/bot.py`, потому что `core/commands.py`'s копия недостижима), терял этот dict
целиком. Здесь то же: рестарт `interface` теряет карту целиком.

Что это значит на практике: следующая `progress`/`sol_progress` для намерения, которое `interface` уже
забыл (потому что рестартовал), увидит «не видели `intent_id`» и пошлёт **новое** сообщение вместо правки
уже существующего в Telegram — то есть после рестарта `interface` посреди сделки один раз получится два
сообщения прогресса (старое, которое просто перестанет обновляться, и новое) вместо одного непрерывного.
Это не поломка доставки (владелец не теряет ни одного отчёта — `execution_notice` DTO в `core_notifications`
никуда не делись, что не подтверждено `ack_notification` — придёт заново тем же путём, что и любое другое
недоставленное уведомление) и не денежный риск (это тот же самый Telegram-текст, который уже отрисовывался
и раньше — эта правка ничего не меняет в том, ЧТО показывается, только в том, СКОЛЬКИМИ сообщениями). Решил
не персистить карту (например, в `interface_state()`) по трём причинам: (а) это прямое продолжение
поведения, которое уже было приемлемым для core весь M1-M4; (б) `interface` уже рестартуется независимо от
`core` по дизайну трёхпроцессной архитектуры (`interface/runtime.py: run_interface` — свой `ExecutionLock`) —
частые независимые рестарты `interface` явно предполагались с самого начала; (в) цена ошибки — одно лишнее
сообщение на рестарт посреди сделки, а не потеря данных или двойное исполнение. Если это решение окажется
неверным (например, рестарты `interface` во время исполнения станут частыми), карту можно сохранять в
`interface_state()` (тот же JSON, что уже хранит `offset`/`acks`) — оставляю это явной, а не тихой, будущей
развилкой.

- **Денежная логика и sim-гейт** — `trade/engine.py`, `trade/sol_flow.py`, `operation_roots.py`,
  `core/commands.py`, `core/journal.py` не менялись вообще (ни одной строки — только читал). `intent_id`
  внутри `facts` как был единственным полем маршрутизации (не рендерится в текст — это не поменялось), так
  и остался.
- **DTO/wire-формат** — `EXECUTION_NOTICE_VERSION`, `EXECUTION_NOTICE_FIELDS` не менялись; версия не
  поднята, потому что форма DTO на проводе между `core` и `interface` не изменилась (`progress_intent_id` —
  внутренний маркер между `present()` и `deliver_once()` внутри процесса `interface`, никогда не уходит в
  `core_notifications`/`ack_notification`).
- **`tg/bot.py` (однопроцессный `funding_bot trader`)** — не трогал: у него edit-in-place уже работает
  (`BotHooks.notice` → `Bot.progress()`), этим багом он не затронут. Не переносил его на `ProgressTracker` —
  вне заявленной задачи (только механизм доставки трёхпроцессного режима), и это отдельная, не денежная
  архитектурная развилка («унифицировать оба режима» или «оставить старый путь как есть, раз он и так
  работает») — решение владельца, не моё.
- **`.env`/ключи/секреты** не читались и не менялись. `trade.db` на VPS не открывался — вся работа в
  клонированной рабочей копии на Маке (`scratchpad/funddd_bot_progress_edit`).
- **Длинные progress-сообщения** (`tg/sender.py: split_text` режет `send()` на несколько кусков при
  переполнении `TG_SPLIT_CHARS`) — `on_done`/`message_id` относятся к ПОСЛЕДНЕМУ куску (см.
  `Sender._deliver`: `res` переприсваивается в цикле по кускам). Значит если однажды текст стадии прогресса
  окажется длиннее лимита, править будет только последний кусок, более ранние останутся статичными. Это не
  новая дыра — ровно то же самое уже происходит с `message_id` плана (`Bot._plan_sent`/`store.set_intent_message`
  берёт тот же `m["message_id"]` от `send()`), не специфично для этого патча и не в его границах.

## Тесты

Новый файл `tests/test_m4_progress_edit_in_place.py` — 19 тестов, три уровня:

1. `ProgressTracker` в изоляции (6 тестов): первый `route()` → `send`, второй до `resolved()` → `wait` (не
   второй `send`!), `resolved()` отдаёт накопленный текст и переключает следующий `route()` на `edit`;
   `resolved(None)` (доставка не удалась) забывает намерение, следующая стадия снова `send`; `forget()`
   чистит known/inflight/pending и идемпотентен; `max_tracked` вытесняет самую старую RESOLVED запись.
2. `present()` с реальными DTO через `core.journal.Outbox`/`Journal` (7 тестов, тот же приём, что уже
   использует `tests/test_m4_domain_notifications.py`): вторая стадия правит то же сообщение с
   `throttle=True`; без `progress=` — старое поведение (всегда `send`) не сломано; каждый из трёх
   терминальных топиков (`halt`/`sol_halt`/`executor_crash`, параметризовано) действительно чистит запись;
   новый `intent_id` после `halt` шлёт новое сообщение, не наследует чужой `message_id`; `sol_progress`
   маршрутизируется так же, как `progress`; пока первый `send` в полёте — `noop`, не второй `send`.
3. `Interface.deliver_once()` целиком (6 тестов) — `FakeSender`, имитирующий асинхронный `on_done`
   `tg/sender.py: Sender` (не резолвится сразу же, а когда тест явно скажет — этим и ловится гонка, ради
   которой существует `_pending`): три стадии подряд правят одно сообщение; **пачка стадий, пришедшая раньше
   ответа Telegram на первый `send`, схлопывается в одну правку с ПОСЛЕДНИМ текстом** (это и есть тест на
   тот самый гоночный случай, который наивная 2-состояний версия трекера пропустила бы); новый `intent_id`
   после `halt` шлёт новое сообщение; неудавшийся первый `send` (Telegram не ответил) — следующая стадия
   повторяет `send`, а не бьётся в несуществующее сообщение (с честной проверкой, что недоставленное
   уведомление само по себе повторно читается по уже существующему в проекте протоколу ack — не специфика
   этого патча); `noop`-уведомление ack’ается сразу локально и не читается вечно (двухфазный ack —
   pending → `ack_notification` на следующем `deliver_once()` — тоже существующий протокол, не мой).

Мутационная проверка ключевых условий (вручную, временная правка → красный прогон → откат, 4 мутации):
отключение ветки `mid is not None → edit` в `route()` уронило 10/19; отключение вызова `forget()` для
терминальных топиков в `present()` уронило ровно параметризованный тест по всем трём топикам (3/19);
возврат `kind='send'` вместо `kind='noop'` в ветке `wait` уронило 4/19 (все — про гонку и двухфазный ack);
удаление flush-правки накопленного текста в `Interface.deliver_once()`'s `on_sent` уронило 3/19 (все — про
пачку во время полёта). Каждая мутация ловится, файлы после каждой восстановлены обратно.
