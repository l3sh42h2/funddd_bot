# ТЗ: переход funding_bot на три процесса и независимые торговые ноги

Версия: 1.2, 14.09.2026. Статус: спецификация; реализация ещё не выполнена.
Исполнитель миграции: **Codex**, назначен владельцем. Три процесса утверждены владельцем.
**Ресайз и ручной SL с автопродажей спота — следующий отдельный патч ПОСЛЕ приёмки миграции.**
Общие правила: [COORDINATION.md](COORDINATION.md). Проверки: [MIGRATION_ACCEPTANCE.md](MIGRATION_ACCEPTANCE.md).

## 1. Цель и границы

Новая площадка подключается адаптером. Комбинация уже поддержанных ног задаётся конфигурацией и проверкой
совместимости. Вход/выход, разрешения, остаток операции, восстановление и учёт не реализуются заново для каждой
пары площадок. Различия транзакций EVM, Solana и биржевых заявок сохраняются в исполнителях.

Три долгоживущих прикладных процесса на одном VPS:
1. `collector` — рыночные данные и публичные таблицы.
2. `core` — сделки, риск, исполнение, подтверждение результатов, учёт и восстановление.
3. `interface` — Telegram, публичный dashboard и приватный кабинет.

Это модульное торговое ядро с изоляцией процессов; Kubernetes, Kafka, Redis, распределённая БД и отдельный сервис
на каждую биржу не требуются. systemd и существующий сетевой туннель — инфраструктура, не дополнительные торговые
процессы. Существующие адаптеры и журналы сохраняются. Удалять `sol_flow.py` ради самого удаления не требуется;
к финалу бизнес-координация из него должна быть перенесена в общие модули, специфическое исполнение может остаться.

В релиз миграции НЕ входят:
- команды добора/нового сокращения и новый SL, реальные защитные ордера, их автоматическое срабатывание;
- реальные адаптеры CEX-спота Bitget/Gate и фьючерсов Lighter/Extended;
- новые разрешённые стратегии, кредит/заём для шорта спота, переводы денег между площадками;
- изменение торговых лимитов, маршрутов по умолчанию, политики продолжения прерванных сделок;
- исправление несвязанных торговых алгоритмов под видом миграции. Блокирующая ошибка фиксируется отдельно.

## 3. Владение данными, ключами и решениями

| Объект | Единственный владелец записи | Как другие получают данные |
|---|---|---|
| Рыночная БД, universe, публичные снимки | collector | Версионированные атомарные снимки |
| trade.db: сделки, команды, операции, действия, исполнения, резервы | core | Локальный IPC и опубликованные проекции |
| Торговые ключи CEX, ключи кошельков, подписи | core | Никому не передаются |
| Telegram offset, очередь доставки, сессии кабинета | interface | Не используются как торговая истина |
| Release manifest/state | процесс deploy под серверным lock | Чтение всеми процессами |

- Только core принимает/отклоняет торговую команду и решает, что разрешено отправить на площадку.
- Collector и interface не открывают trade.db даже на запись «только одной служебной таблицы».
- Interface не пересчитывает объём, риск или PnL из сырой торговой БД. Он отображает DTO ядра.
- Торговые изменения owner-конфигурации проходят валидатор core и имеют config revision. Существующая ручная
  правка owner.toml сохраняется, если текущий процесс это поддерживает, но core перечитывает/валидирует её перед
  действиями и отражает revision. UI не получает права менять файл напрямую.
- Core стартует без Telegram-токена и при недоступности Telegram. Сбой UI не останавливает контроль начатых действий.
- Отказ collector блокирует новые решения, которым нужны свежие данные, но не запрещает восстановить отправленный
  ордер или закрыть известную позицию по свежим прямым данным адаптера согласно прежним ограничениям.

Целевые Unix-пользователи: отдельные collector/core/interface; runtime с ограниченными каталогами и группами.
Core владеет trade.db и ключами; UI получает только доступ к своему состоянию, публичным снимкам и core socket.
`.env` разделить на collector.env/core.env/interface.env вне Git. Collector получает лишь нужные ключи данных/
котировок; interface — TG token и кабинет; core — торговые и нужные ему ключи маршрутов. Секреты не копировать в
снимки/DTO/логи. Общая квота OKX учитывается одним межпроцессным ограничителем по аккаунту провайдера; разделение
процессов не должно удвоить допустимую частоту запросов. Приватные документы защищены прежней авторизацией кабинета.

## 4. Общая модель сделки

`Trade` содержит ID, strategy/policy ID, две `LegSpec`, статус, config revision и ссылки на операции.
`LegSpec` содержит:
- стабильный leg_id, роль в стратегии, тип рынка `spot|perpetual`, направление целевой экспозиции;
- adapter_id, venue/account/subaccount, сеть/genesis/chain ID там, где это необходимо;
- исходный instrument ID площадки, canonical asset identity с доказательством соответствия;
- количество в единицах площадки, базовую экспозицию, decimals/step/tick, multiplier;
- валюты котировки, расчёта, маржи и комиссий; capabilities и версию спецификации.

Идентичность актива не определяется одним тикером или близостью цен. У сетевого токена сохраняется адрес/mint,
у фьючерса — полный инструмент, рынок и аккаунт (включая HIP-3 dex). EVM-адреса нормализуются по байтам только в
соответствующих полях; Solana mint/fullcoin и произвольные ID не переводятся целиком в lowercase.
Существующие inst_json/inst_hash и ID сделок не переписывать. Новая модель имеет versioned mapping поверх старых
записей; несовместимые или недоказанные единицы дают явный отказ, а не m=1 по умолчанию.

Денежные суммы и количества — Decimal/целые raw, в JSON строки. Нельзя склеивать USDT и USDC в одну сумму без
явного курса и времени его получения; для хеджа сравнивать базовую экспозицию с учётом multiplier.

Первые live-политики сохраняют существующий long spot / short perp. Модель двух ног не должна требовать фиктивного
спота, кошелька или газа для CEX-спота и perp/perp. Возможность последних проверяется на фейках, но их live-запуск
и новые стратегии не включаются в миграцию. Спот-short без отдельной модели займа считается неподдержанным.

## 5. Контракты адаптеров и общая сборка

Адаптер не знает venue второй ноги и не управляет всей сделкой. Он предоставляет:

| Метод/результат | Назначение |
|---|---|
| `capabilities()` | Типы рынков/действий, short, reduce-only, price trigger, исполнение по сумме/количеству |
| `describe(instrument_ref)` | Идентичность, единицы, ограничения, metadata revision |
| `observe(account, instrument)` | Баланс/позиция/маржа с as_of, source и качеством |
| `quote(action, bounds)` | Исполнимый план с max spend/min receive, сроком и разложением расходов |
| `prepare(action_id, quote)` | Подготовка отслеживаемой попытки; не объявлять исполнением |
| `submit(prepared)` | Отправка только после сохранения попытки и разрешения core |
| `resolve(attempt_ref)` | Авторитетный исход, исполненные количества, комиссии, доказательства |
| `cancel(ref)` | Отмена, если поддерживается; результат может быть неизвестным/частичным |
| `read_executions(cursor)` | Инкрементальные исполнения с ключами дедупликации и полнотой страниц |

Названия могут уточняться без изменения смысла контрактов. Optional-возможность имеет явное UNSUPPORTED, а не
пустую реализацию. Native SL в этой миграции только описан capability; установка SL реализуется следующим патчем.

Общий результат сохраняет `ACCEPTED`, `PARTIALLY_FILLED`, `SETTLED`, `CANCELLED`, `REJECTED`, `UNKNOWN`, executed
quantity и evidence. CANCELLED не означает нулевого исполнения. Поля finality/commitment и provisional сохраняются:
CEX acknowledgement, Solana confirmed и доказанное завершение действия не взаимозаменяемы. Политику финальности
существующих путей не ослаблять. Исход неизвестен — новый независимый запрос взамен старого не создаётся вслепую.

Ошибки core: invalid_request, unsupported, insufficient_funds, rejected, rate_limited, transient, unknown_result,
identity_mismatch, stale_data, configuration. Сырой код/текст сохраняется редактированным в evidence адаптера.
Повтор допустим только по классу исхода и idempotency, а не потому что exception назван transient.

Реестр `AdapterRegistry` независимо собирает ноги по конфигурации. Профили bsc_okx_aster/rh_okx_gate/
sol_best_hyperliquid остаются совместимыми aliases на две LegSpec, enabled и limits; они не выбирают отдельную
реализацию входа. Gate credentials не должны зависеть от успешной инициализации legacy Aster, а EVM-кошелёк другой
сети — от включения профиля BSC. Credential provider загружает и выдаёт нужные секреты одному адаптеру без повторной
разрушительной загрузки общего env. Режим каждой ноги учитывает profile mode и фактически доступные полномочия.

Специфические компоненты сохраняются:
- EVM: маршруты OKX, allowance, gas/nonce, подпись, receipt и восстановление;
- Solana: Jupiter/OKX, проверка маршрута, ATA/rent, blockhash, подпись, финальность и восстановление;
- Futures: инструменты/аккаунты/маржа/заявки/исполнения/фандинг конкретной биржи.

### 5.1. Четыре класса подключаемых площадок — обязательное требование владельца

Поддержать независимые признаки `venue_kind = cex|dex` и `market_kind = spot|perpetual`:

| Класс | Особенности внутри адаптера |
|---|---|
| CEX spot | Биржевой баланс, заявки/частичные исполнения, комиссии; без фиктивного газа/кошелька |
| CEX futures | Контрактные единицы, маржа, long/short, reduce-only, позиции и funding |
| DEX spot — EVM | Swap/маршрутизация, allowance, gas/nonce, chain ID, подпись и receipt/finality |
| DEX spot — Solana | Swap/маршрутизация, mint/ATA, rent, blockhash, подпись и commitment/finality |
| DEX futures | Позиции/маржа/контракты плюс модель подписи, collateral и финальность конкретного протокола |

DEX futures не равен DEX swap; он не обязан иметь allowance/swap-интерфейс. Venue kind не определяет транспорт:
у DEX могут быть API/order book, у конкретного протокола — свои on-chain действия. Эти различия не протекают в
координатор сделки. Здесь futures означает бессрочные контракты текущего бота; поставочные/срочные контракты
потребуют отдельной модели expiry/settlement и не считаются автоматически поддержанными.

Подключение площадки в рамках существующих capabilities состоит из адаптера, регистрации в AdapterRegistry,
конфигурации/секретов и contract/recovery тестов. Не требуется менять OperationController, Ledger/PnL, Telegram
или писать путь «новая площадка × каждая старая». Предоставить шаблон адаптера и краткую инструкцию подключения.
Новая capability требует явного расширения контракта и проверки; пустая заглушка не считается поддержкой.

DEX spot обязательно поддерживает две семьи сетей: `evm` и `solana`. Семейство сети — отдельный признак
адаптера; конкретная сеть EVM задаётся chain ID/RPC и проверенными параметрами. Обе реализации используют
единый контракт spot и общий OperationController. Путь под каждую пару EVM/SOL × futures не создаётся.

Приёмка: независимо подключить пять синтетических адаптеров четырёх классов (DEX spot отдельно EVM и Solana) через тот же механизм,
что используется production; проверить совместимые сочетания spot/perp и perp/perp, обе стороны каждой ноги,
отказы неподдержанного short/reduce-only, единицы/частичные исполнения/UNKNOWN. Показать diff подключения:
новые файлы адаптера/тестов и запись регистрации/конфигурации, без правок бизнес-координатора и учёта.
Это доказательство расширяемости. Реальные новые площадки требуют своих интеграционных проверок и разрешения
live-комбинации; наличие общего интерфейса не доказывает безопасность любого сочетания инструментов.

## 6. Core: координация, учёт и восстановление

Общий `OperationController` обрабатывает только существующие пользовательские действия: propose/approve entry,
exit (включая существующий частичный), rehedge, undo, допустимое resume, pause. Новые resize/SL команды отключены.
Внутренние операции имеют неизменяемую цель, границы одобрения и связь всех продолжений; это основа следующего патча.

`Operation` → `Action` каждой ноги → `Attempt` → `Execution/Fee`. Одна операция может иметь много клипов и попыток.
Сохранять намерение ДО внешнего действия. Не держать транзакцию SQLite открытой во время сетевого запроса.
Подтверждённый остаток считается по фактам конкретной операции за вычетом уже зарезервированного/in-flight объёма;
не по всем историческим покупкам сделки. Существующие semantics resume сохраняются совместимыми преобразователями.

Один логический координатор на сделку, один активный core на VPS (kernel flock на стабильном пути вне release).
Пока сохраняется нынешняя глобальная сериализация торгового исполнения; увеличение параллелизма не входит в ТЗ.
В БД — условные переходы состояния/версии и уникальные ограничения активных операций. Резервы по аккаунту/валюте
учитываются совместно для всех сделок. Nonce/signing queues сериализуются по реальному account/wallet scope.
Старый trader должен брать тот же execution lock до переходного выката; невозможно держать два владельца отправки.

Журналы исполнения и Ledger внутри core:
- старые DEX/HL/CEX evidence и таблицы сохраняются; новые общие события ссылаются на них через стабильные ключи;
- execution dedup key определяется адаптером с venue/network/account/instrument там, где ID не глобален;
- денежные движения, комиссии, funding, количества и PnL вычисляются по исполнениям, а не по отправленным заявкам;
- нормализованный event и обновление учётной проекции/outbox коммитятся атомарно в trade.db;
- несколько валют не суммируются молча, неизвестное не равно нулю; cost basis/PnL должны совпасть с прежним
  проверенным расчётом на одном временном срезе в пределах только заранее определённого округления вывода;
- существующие operations/operation_intents для SOL переиспользовать через mapping. Не создать вторую независимую
  активную операцию поверх первой. Новые таблицы, если нужны, получают отдельные имена `core_*` и миграции.

При рестарте core сначала загружает журналы, резервы и unresolved attempts; восстанавливает наблюдения и сверяет
позиции. При несоответствии — состояние с причиной и запрет на наращивание, без выдуманного flat.
Миграция не даёт новых полномочий на автоматическое продолжение старых ручных операций. Resume сохраняет прежнее
требование подтверждения, где оно было. Автоматическое восстановление SL будет отдельным правилом следующего патча.

## 7. IPC и интерфейс: конкретный протокол v1

Один локальный Unix-domain stream socket `/run/funding-bot/core.sock`, без внешнего TCP-порта. Каталог/сокет имеют
ограниченные owner/group/mode; core проверяет peer credentials. Разрешённый UI peer и deploy peer различаются.
Транспорт на стандартной библиотеке: 4-байтовая длина big-endian + UTF-8 JSON, максимум 1 MiB на кадр. Большие
ответы только с пагинацией. Не добавлять брокер сообщений ради трёх локальных процессов.

Запрос: `protocol_version`, `request_id`, `method`, `actor`, `idempotency_key`, `payload`.
Ответ: тот же request_id, `ok`, `result` либо типизированная `error`, `core_version`, `state_revision`.
Неизвестная версия/метод, лишние опасные поля и слишком большой кадр отклоняются. Таймаут управляющего вызова
по умолчанию 5 секунд; долгая работа возвращает durable operation/request ID, завершение приходит отдельным событием.

Обязательны ограниченная очередь и лимиты соединений/запросов, таймаут чтения кадра и backpressure.
При перегрузке новый запрос получает busy до durable acceptance; уже принятые запросы не теряются.
Recovery/учёт начатых действий не вытесняются запросами UI; сетевое исполнение не блокирует IPC loop.
Конкретные лимиты фиксируются конфигурацией и проверяются нагрузочным тестом.

Методы v1:
- submit_user_command(raw_text, Telegram source IDs), get_request(id);
- approve_plan(plan_id, nonce, plan_hash, expected_revision), reject_plan;
- get_status, list_positions, get_deal (DTO с пагинацией);
- read_notifications(after_cursor), ack_notification(event_id, delivery_state);
- begin_drain/get_drain_state — только deploy peer, не команда публичного интерфейса.

UI сохраняет исходные Telegram update/callback IDs. Core независимо проверяет owner/user/chat из доверенного
локального peer, тип команды, TTL, nonce, инструмент, режим и revision. UI не может обойти эти проверки через IPC.
Повтор одного idempotency key возвращает сохранённый результат; тот же key с другим payload отклоняется.
Таймаут ответа после принятия не означает «не принято»: UI узнаёт get_request или повторяет ТОТ ЖЕ ключ.

`command_inbox` core имеет уникальный ключ источника; принятие команды и её результата атомарно сохраняется.
Telegram offset продвигается только после durable acceptance либо durable отказа. Повтор доставки после сбоя
безопасен. Устаревшие команды не исполняются после восстановления связи без нового плана/подтверждения.
Если core недоступен, UI явно сообщает, что команда/стоп не применены; не выдаёт локальную очередь за выполнение.

События UI читаются по монотонному cursor, подтверждения доставки хранятся. Отправка Telegram и commit БД не
атомарны: после сбоя возможен повтор УВЕДОМЛЕНИЯ. Не обещать exactly-once Telegram; повтор не создаёт ордер.
Уведомления содержат стабильный event/operation ID. UI не имеет доступа к raw signatures или trading secrets.

Рынки collector публикует атомарными снимками с schema_version, snapshot_id, generated_at и возрастами источников.
Core публикует приватные read-model DTO/снимки отдельно с revision/as_of/quality. Если UI показывает сохранённую
проекцию во время отказа core, она явно помечена устаревшей, торговые подтверждения отключены. Публичная таблица
никогда не получает торговые данные. Сессии/CSRF/авторизация кабинета сохраняются.

## 8. Перенос файлов: текущие точки → целевые обязанности

Предлагаемые каталоги: `contracts/`, `core/`, `adapters/`, `ipc/`, `interface/`. Не перемещать неизменённые файлы
ради красоты: допустимы совместимые импорты и тонкие обёртки с явной датой/этапом удаления.

| Сейчас | Целевая обязанность / действие |

| tg/bot.py::run_trader, build_trader_legs | Сборка торговли → core/bootstrap; Telegram transport → interface |

в адаптере, а решение разрешить операцию — в core. Межмодульные зависимости проверяются тестом архитектурных границ.

## 9. Поэтапная миграция и обязательные результаты

### M0. Зафиксировать базу и владение — без изменения торговли
- Сверить полный Git/file manifest сервера; собрать состояние schema, enabled profiles, открытых/paused сделок,
  unresolved intents/DEX/SOL/HL attempts, cursors, очередей, service PID/version и режимов. Без секретов в отчёте.
- Подтвердить окончание пересекающихся изменений Claude по Git/патчноутам, сохранить его FATCOIN и ANSEM fixes.
  Новые пересечения решает владелец по COORDINATION. База документов main не считается базой боевого кода.
- Снять согласованный SQLite backup штатным backup API, включая состояние WAL; не копировать один .db из живого WAL.
- Сохранить replay fixtures с синтетическими секретами; реальные пользовательские данные не публиковать в Git.
Выход: BASELINE.md, полный manifest, перечень состояний/инвариантов и предварительный план миграций.

### M1. Выделить headless core и безопасный канал команд
- Вынести bootstrap/loop торговли из Telegram. Добавить singleton, IPC v1, inbox/outbox, typed DTO.
- Сначала использовать старые engine/SolEngine внутри временных compatibility wrappers, без изменения алгоритмов.
- Interface отделить от торгового исполнения. Сохранить старые команды/кнопки и их проверки; просроченные или
  несовместимые старые кнопки отклонять, не молча подтверждать заново.
- Полностью отделить TG offset от торговой записи; миграция offsets/inbox не должна повторить старую команду.
Выход: core работает без Telegram; остановка интерфейса не прекращает учёт/восстановление; AC-01..06.

### M2. Разделить данные UI и секреты процессов
- Убрать прямые SQL-запросы кабинета в trade.db; создать версионированные read models.
- Разделить env/права; сохранить общий rate limit провайдеров. Убрать public/private утечки.
- Добавить лёгкие health/readiness каждого процесса и /status UI с реальными версиями/as_of/ошибками источников.
Выход: три процесса соблюдают таблицу владения, тяжёлая таблица не участвует в health; AC-07..10.

### M3. Независимые ноги и общие результаты
- Обернуть существующие адаптеры контрактами §5, вынести из общей логики venue-specific errors/HL preflight.
- Создать AdapterRegistry и независимый credential provider; сохранить aliases старой конфигурации.
- Проверить EVM и Solana с каждым существующим futures-адаптером на фейках подходящих инструментов/аккаунтов.
  Не включать live-комбинацию без фактического листинга, идентичности, настроек и разрешения владельца.
- Добавить fake CEX-spot и fake perp/perp для доказательства отсутствия блокчейн-зависимостей в общем контракте.
Выход: новая совместимая комбинация не требует правок координатора/Telegram/PnL; AC-11..14.

### M4. Общие операции, Ledger и recovery
- Вынести из обоих путей общий жизненный цикл существующих операций, ограничения, reservations и transitions.
- Подключить старые журналы через детерминированное отображение; выполнить replay и сравнение балансов/PnL/
  состояний. Не требовать закрытия исторических сделок ради изменения классов Python.
- Теневая сверка выполняет расчёты на записанных данных без подписи, отправки, nonce allocation или live reservations.
  Старый и новый код не должны одновременно торговать. В тени нет второго независимого writer trade.db.
- После доказанной эквивалентности удалить дубли общих правил; специфические исполнители не переписывать без нужды.
Выход: одинаковые операции и восстановление для обеих сетей, сохранённые исторические hashes; AC-15..20.

### M5. Выпуск, переключение и приёмка
- Выполнить §10 и матрицу приёмки, независимое ревью денежного пути и плана отката.
- На реальном VPS — сначала проверка конфигурации/совместимости только для чтения; новая архитектура не должна
  отправлять тестовый ордер. Живые сделки для доказательства миграции автоматически не открывать.
- После переключения сверить текущие позиции, исполнения, незавершённые операции, версии процессов и PnL на
  согласованном срезе; обработать законные внешние изменения, не сравнивать разные моменты как равные.
- Зафиксировать MIGRATION_RESULT.md и release receipt. Только после выполнения критериев патч считается принят.
Выход: миграция установлена и проверена; затем отдельная ветка/релиз resize+SL от принятого SHA.

Этапы дают отдельные reviewable commits. Допустимы промежуточные релизы с проверенной совместимостью; каждый
переключаемый этап проходит применимые проверки. Одобрение направления не означает, что результаты уже получены.

## 10. Выкат, производительность процесса разработки и откат

До внедрения нового механизма применяется существующий deploy/deploy.sh; ручные подмены/рестарты запрещены.
Изменения самого deploy входят в M5 (раньше допускаются отдельным проверенным коммитом), чтобы конечная схема
не наследовала повтор полного набора при каждом retry.

Целевой deploy разделяет `build+verify` и `install verified artifact`. Проверка артефакта привязана к source tree
SHA, lock/dependency hashes, Python/platform/runtime fingerprint, тестам/фикстурам/конфигурации и хешу артефакта.
Полный набор один раз в совместимом Linux-окружении; Mac-specific UI тесты отдельно. На VPS — короткая проверка
импортов/установки/конфигурации/процессов. При неизменном артефакте retry повторяет актуальные preflight/health,
но не весь pytest. Не применять такую оптимизацию к непроверенному или изменённому окружению.

Серверный deploy — один supervised job под flock, переживающий потерю SSH. Releases неизменяемы, runtime/секреты
вне дерева release. `release-state.json` содержит установленные source/artifact hashes, версии компонентов/IPC/schema,
active epoch и результат проверки. Под lock проверяется expected_base; несоответствие — STALE_BASE до изменений.
Встроенная версия процесса берётся из его загруженного build manifest, не из изменившегося symlink на диске.

Порядок переключения:
1. Проверить источник/артефакт, совместимость schema/IPC, диск/backup, текущую базу и незавершённые действия.
2. Включить drain: новые открытия/изменения не принимаются, начатые разрешаются по прежней политике. Любые
   недопустимые unresolved действия блокируют переключение. Не выключать исполнителя ради красивого таймаута.
3. Завершить старый trader/core, убедиться в освобождении общего execution lock, только затем запустить новый core.
   Все процессы читают код собственного неизменяемого release, не смешивают загруженные и новые файлы.
4. Новый core выполняет recovery и миграционную проверку, публикует readiness; затем подключается совместимый UI.
5. Снять drain только после проверки согласованности. При ошибке сохранить причину и выполнить совместимый откат.

Новые systemd units: funding_bot-collector, funding_bot-core, funding_bot-interface. Старые trader/web отключаются
в переключении; служба trader и новый core никогда не остаются параллельно владельцами отправки. Туннель/URL/порт
публичного интерфейса сохранить. UI-only релиз не перезапускает core, если manifest доказывает совместимость IPC,
DTO и отсутствие общих изменений. При неясном влиянии — полный применимый цикл.

Откат возвращает КОД, а не старую trade.db поверх состоявшихся исполнений. Миграции additive на переходе;
версия min_reader/schema проверяется до установки и отката. Идемпотентный migration runner сначала dry-run,
затем backup/transaction/checks; не создавать пустую БД при ошибке пути. Форматы, которые старый код не понимает,
блокируют откат на него: сохраняется текущий recovery-capable core в drain либо устанавливается совместимый fix.
План фикса без отката обязателен для необратимого перехода; универсальный автооткат в старую .prev недопустим.

Health endpoints/локальные ответы ограничить 16 KiB, не читать полные таблицы и не делать запросы на биржи.
Цель локальной выдачи health p95 < 200 мс на тестовом профиле нагрузки, зафиксированном в отчёте. Readiness
отражает реальное состояние loop/recovery/as_of, а не просто наличие PID. Сохранить действующее требование свежести
рыночных данных; новый снимок статуса не делает старые данные свежими. Полная загрузка dashboard не должна
задерживать обработку команд core; это проверяется нагрузочным сценарием, а не объявляется по разделению процессов.

## 11. Приёмка, отчётность и передача следующего патча

Применяется вся матрица MIGRATION_ACCEPTANCE.md. Повтор тестов только при новых изменениях, провале или
непокрытом риске; полный набор не дублируется вручную перед механизмом, который его гарантированно запускает.
Один независимый reviewer проверяет контракты/миграцию/восстановление/откат; его замечания получают ответ и проверку.
Владелец реализации — Codex. Задачи Claude не присваиваются; фактические пересечения обсуждаются по общим правилам.

Отчёт каждого этапа: базовый/новый SHA, изменённые обязанности, проверки, несовпадения, rollback boundary,
длительность работы/тестов/ревью/выката, модели и доступные usage counters. Не выдавать cached tokens за новый input,
не обещать заранее «миллионы токенов» или срок без оценки конкретного этапа. После M0/M1 уточнить оставшуюся оценку
на основании измеренного объёма; ожидание/сбор метрик выполняют скрипты с компактным выводом.

Приёмка миграции не включает работоспособный новый resize или SL. Патч этих функций начинается от принятого release
SHA и использует новый OperationController, Ledger, reservations, adaptive leg quantities и будущий stop capability.
Уже согласованные требования сохраняются: ручная цена SL для будущих входов, native futures stop, одна фоновая
проверка позиции в 60 секунд, автоматическое закрытие спота по доказанному исполнению. Уточнение поведения входа
без SL остаётся в следующем патче и не блокирует миграцию. Старые позиции не получают SL автоматически.

## 12. Предварительная оценка времени

Оценка Codex для планирования, не измеренная длительность и не гарантия срока: **20–35 часов активной работы**.
При 7 часах доступной работы в день — ориентировочно 3–5 рабочих дней; ожидание лимитов подписки, внешнего ревью,
решения пересечений и безопасного окна переключения добавляется отдельно. Это не обещание фонового выполнения.

| Работа | Предварительно |
|---|---|
| M0: актуальная база, состояния и план совместимости | 2–3 ч |
| M1–M2: процессы, IPC, UI, права и снимки | 4–7 ч |
| M3–M4: четыре класса адаптеров, общий координатор и перенос состояния | 7–12 ч |
| Проверки, независимое ревью и исправления | 5–9 ч |
| M5: механизм установки, переключение и проверка результата | 2–4 ч |

Оценка предполагает переиспользование существующего исполнения, отсутствие новой торговой стратегии и работоспособную
базу. Главная неопределённость — совместимость незавершённых EVM/SOL операций и объём доработки deploy. Если M0/M1
покажут больший объём, пересмотреть прогноз до продолжения следующих этапов; не скрывать превышение в конце.
Реальные новые биржи, ресайз и SL в эту оценку не входят. Уточнение четырёх классов включено в оценку и приёмку.
