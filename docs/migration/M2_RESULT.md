# M2 — реализация и проверка границ процессов

Статус: реализовано в рабочей ветке; боевое переключение относится к M5. Финальный повтор Linux-проверки после
последних защитных правок ожидает явного разрешения пользователя, затребованного автоматической проверкой.

## Изменения

- Production Cabinet получает только приватный versioned DTO через IPC. SQL/расчёт вынесены в core/readmodel.py.
  Explicit db_path backend оставлен только для прежних offline tests/tools; instance() и interface его не выбирают.
- Денежные Decimal передаются lossless как типизированные строки; числовые тикеры не преобразуются в числа.
  Пагинация закреплена за revision; изменение снимка требует повторного чтения целиком, частичные данные не выдаются.
  Старый/недоступный core даёт явную ошибку кабинета, не нулевые «актуальные» позиции.
- Collector публикует schema_version/snapshot_id и маленький отдельный health. /status больше не читает table.json.
  Истинный возраст tick/source сохраняется; неизвестная версия/частичный новый snapshot не считаются свежими.
- Core health содержит captured source fingerprint, PID/boot ID, готовность, drain, текущую живость loop.
  Interface пишет собственный health; проверка Telegram не блокирует запуск HTTP, восстановление сессии по таймауту.
- Runtime/owner/table/trade DB/общий OKX pace имеют отдельные env-пути. В split-режиме ошибка общего pace не
  переводит каждый процесс на собственную квоту: запрос отказывается.
- deploy/migration содержит три unit-шаблона, подготовку изолированных env и точный контракт прав/групп.
  Collector не получает trading keys, interface не получает биржевые ключи, core не получает TG/cabinet секреты.
  Код подготовки только staging: он не стартует службы и не копирует боевую БД. Реальная установка — M5.

## Проверки и ограничения доказательств

- Полный регрессионный набор на Mac: 2164 passed, 2 skipped, 147.05 с. Этот прогон был до нескольких заключительных
  защитных правок; после них повторялись затронутые тесты, а не весь неизменный набор.
- Последующий широкий профиль: 215 passed, 9.61 с (M1/M2, Telegram, кабинет, serve, OKX).
- Дополнительные профильные проверки schema/конфигурации и lifecycle указаны в патчноуте после окончательного прогона.
- Предыдущий Linux-профиль: 28 passed, 6.56 с; Linux root-only DAC fixture: 1 passed, 0.06 с.
  Данные и ключи синтетические, никакие пользователи/службы VPS не создавались. Числовые UID использовались только
  в дочерних процессах одноразового /tmp каталога. Лог и SHA архива — M2_LINUX_TESTS.txt.
  Этот Linux-прогон не доказывает проверку более поздних изменений; повтор заблокирован auto-review и не подменяется
  старым результатом. Блокировка касается передачи исходников на VPS, не запуска торговых ордеров.
- Локальный нагрузочный сценарий: 46 137 501 байт (44 MiB padding), 3 клиента /data.json, 9 скачиваний, 60 /status.
  p95=0.87 мс, max=220.21 мс. Это результат данного синтетического профиля на Mac, не SLA VPS. На боевом VPS
  нагрузочный тест не запускался. M2_LOAD_TEST.txt содержит фактический вывод.
- Независимый reviewer реализации не назначен владельцем; его проверка остаётся обязательной перед M5.
- Pure legacy-formatters внутри совместимого command/engine слоя сохраняются до M3/M4. Импорты Telegram API,
  web server и SQL из production-интерфейса изолированы; полная бизнес-унификация ещё не выполнена и не заявляется.

## Что не менялось

Торговые алгоритмы engine/SolEngine, активные лимиты/профили, позиции и VPS services. M3/M4/M5, resize и SL не
реализовывались. Общий drain M1/M2 явно возвращает safe_to_switch=false до полного release/schema/recovery gate M5.

## Перед следующим этапом

Дождаться разрешённого финального Linux-профиля, затем M3 продолжать от опубликованного SHA этой ветки после fetch
и чтения чужих патчноутов. Не считать main (ветку документов) текущей боевой базой. До M5 не устанавливать unit-шаблоны
вручную и не открывать тестовые живые сделки. Обязательный M5 должен доказать перенос runtime/keys/offsets и права
реальных service accounts, а не только тестовых UID.

Заключительный локальный профиль M1/M2 после интерфейсного health: 31 passed, 5.96 с.
