Правила именно этого проекта (не всех проектов VPS). Утверждены владельцем 13.09.2026. Менять только по решению
владельца. Дополнения по эффективности утверждены владельцем 14.09.2026 (§6). Общая таблица моделей —
`/Users/admin/Documents/vps/CLAUDE.md`; для FUNDING новые правила §6 имеют приоритет при конфликте.

Основание: предложение Codex `/Users/admin/Documents/hyper/reviews/FUNDING_CODEX_CLAUDE_COORDINATION_PROPOSAL.md`
и ответ Claude. Ниже помечено, что уже работает, а что только принято и ещё не внедрено.

## 1. Кто что делает — решает владелец
- Владельца каждой задачи, исполнителя и ревьюера назначает владелец. Агенты задачи между собой не делят и чужие не
  забирают.
- Перед началом задачи агент проверяет пересечение с незаконченными задачами другого агента: движок, учёт денег,
  схема БД, выкат, общие файлы. Если пересечение есть — сообщает владельцу риск и ждёт его решения (параллельно,
  подождать, кому ревью).
- Денежный код ревьюит тот, кого назначит владелец; уровень модели ревью — по `vps/CLAUDE.md`.

## 2. Код и рабочие копии
- Общая история — приватный репозиторий GitHub. Каждый агент работает в своей рабочей копии и своей ветке:
  `claude/<задача>`, `codex/<задача>`. Одновременно одну папку не правят.
- Базовая версия R0 — код, выкачанный на VPS 13.09.2026 13:51 UTC (фаза 1 + рейтинг A/B/C), сверенный по SHA-256
  всех 147 файлов с сервером: `/Users/admin/Documents/vps/funding_bot_releases/R0/`.
- В Git НИКОГДА: `.env*`, `runtime/`, базы (`*.db`), логи, ключи, botLP, подписанные транзакции. Перед каждым
  пушем — проверка кода на точные значения ключей (имена файлов, без значений).
- Отсутствие Git-конфликта не доказывает, что денежные инварианты целы: объединённую версию проверяют тесты и ревью.

## 3. Патчноуты
Каждое изменение — свой файл `PATCHNOTES/<change_id>.md`: автор, задача, исходная база (релиз/SHA), проблема и
результат, затронутые файлы и инварианты, проверки, миграции и совместимость с открытыми сделками, ограничения
отката. Один общий файл одновременно не правят.

## 4. Выкат — один путь для обоих
Выкат только через `deploy/deploy.sh` (тесты на Маке и на сервере, замок, проверенная прежняя версия, автооткат).
Руками файлы на VPS не правят и службы в обход не перезапускают.

Принятый минимум, который ЕЩЁ НЕ ВНЕДРЁН (внедряет тот, кому поручит владелец):
- весь серверный цикл выката — одним процессом под `flock` на сервере (обрыв связи с Маком ничего не ломает);
- `release-state.json`: номер релиза и SHA; выкат с устаревшей базы — отказ `STALE_BASE` без замены файлов;
- обязательный патчноут для выката;
- трейдер сообщает свою версию в `/status`; выкат не считается успешным, пока трейдер не запущен на новой версии;
- отказ до переключения не выдаётся за «откат» (сейчас любой сбой `remote_switch.sh` запускает общий откат);
- drain трейдера перед переключением: новые операции не принимаются, неизвестные исходы разрешены.
Уже работает: замок `mkdir` с токеном, `.prev` = последняя проверенная версия, ворота трейдера (одобренные/
выполняющиеся операции), ворота множителя контрактов при откате.

## 5. Открытые позиции
Открытая захеджированная сделка сама по себе не запрещает выкат, если новая версия умеет её восстановить.
Откат кода не восстанавливает старую `trade.db` поверх состоявшихся сделок.

## 6. Эффективность — решение владельца 14.09.2026

Действует для FUNDING, для Codex и Claude. Это согласованные правила работы и требования к инфраструктуре;
само изменение документа НЕ означает, что новый deploy уже реализован.

Что соблюдаем сразу:
- Оценивать область влияния и денежные инварианты, а не только количество строк или расположение файла.
- Для локального понятного исправления — один исполнитель среднего уровня и одно короткое независимое ревью
  изменения и профильных тестов, когда затронут денежный путь. Рутине и изменениям документации отдельный агент
  не нужен. Сложность/неоднозначность, исполнение ордеров, учёт, подпись, новая связка и авария требуют усиления.
  Конкретный владелец задачи между Codex и Claude по-прежнему выбирается пользователем. Не заявлять смену модели,
  если она фактически не происходила; сообщать реально использованные модели и усилие, если они известны.
- В разработке запускать профильные тесты и проверки затронутых инвариантов. Не дублировать полный набор вручную
  перед deploy, если тот гарантированно выполнит тот же набор. После нового изменения или ошибки — необходимые
  повторные проверки. Документация без изменения поведения бота не требует полного pytest и боевого выката.
- Стандартные действия и ожидание выполняет скрипт; агент получает компактные результаты и разбирает ошибки.
  Не перечитывать без причины большие логи, весь репозиторий и всю историю; ревьюеру передавать задачу, diff,
  инварианты и результаты. Сообщения о прогрессе короткие, без повторного анализа неизменившегося состояния.
- В итогах указывать время подготовки/ревью, тестов, выката и повторов, модели и доступные счётчики токенов.
  Не выдумывать отсутствующие метрики. Разделять cached input, новый input и output; reasoning — часть output,
  не прибавлять его второй раз. Счётчики токенов не равны известному списанию процентов подписки.

Требования к реализации (ещё НЕ внедрены этим изменением; исполнителя назначает владелец):
1. Разделить проверку сборки и установку проверенной сборки. Повтор использовать только при совпадении SHA
   исходников, зависимостей, Python/платформы, набора и конфигурации тестов, идентичности готового артефакта.
   Результат проверки привязывать к артефакту, не к изменяемой ветке. Изменение любого условия отменяет повторное
   использование. При каждом выкате заново проверять текущую серверную базу, незавершённые операции и здоровье.
2. Полный набор один раз в отдельном совместимом Linux-окружении. На VPS — проверка установки, импортов,
   конфигурации и запуска. Платформенные тесты Mac/JavaScriptCore выполнять отдельно. Профиль проверок учитывать
   область влияния; при неясном влиянии расширять проверки. Измерять медленные тесты перед оптимизацией.
3. Маленький статус здоровья без разбора полной таблицы: версия, PID, состояние и время реального обновления.
   Он не должен скрывать устаревшие данные. Перезапускать только затронутые компоненты после проверки зависимостей;
   при неясной области влияния — полный цикл. Замок, проверка базовой версии и защита открытых операций сохраняются.
4. Модели и контекст выбирать соразмерно задаче по правилам выше; обычную механику автоматизировать скриптами.
5. Автоматически сохранять длительности стадий, результаты и доступную статистику использования моделей в отчёт.

До реализации и проверки нового механизма §4 остаётся действующим: не обходить проверки старого deploy флагами,
ручной заменой файлов или рестартами. Цель 5–10 минут для локального исправления при исправной инфраструктуре —
ориентир, не гарантия и не основание для пропуска обязательных проверок.

## 7. Как оба агента узнают о чужих изменениях

- Общий источник правил: `docs/COORDINATION.md` в `origin/main` приватного `l3sh42h2/funding_bot`.
  Перед новой задачей выполнить `git fetch origin`, прочитать `git show origin/main:docs/COORDINATION.md`,
  посмотреть новые коммиты и относящиеся к задаче патчноуты в main и рабочих ветках. Fetch не меняет рабочие файлы.
  При недоступности GitHub явно отметить, что актуальность правил/веток не подтверждена.
- Не делать автоматический pull/merge в чужую или грязную рабочую копию. Новая запись в GitHub не обновляет
  автоматически уже работающего агента и его ветку. Новые правила применяются после их чтения.
- Для назначенной пользователем задачи создавать собственный `PATCHNOTES/<change_id>.md` уже при начале работы:
  задача, исполнитель, назначенный ревьюер (или «не назначен»), базовый SHA, ветка, затрагиваемые файлы/компоненты,
  статус (`in_progress`, `review`, `ready`, `deployed`, `blocked`) и время обновления. Публиковать в своей ветке.
  Это уведомление о занятой работе, а не самостоятельное назначение владельца и не технический замок.
- По завершении дополнять тот же патчноут результатом, проверками, совместимостью и ограничениями; для состоявшегося
  выката можно добавить отдельный неизменяемый отчёт с установленным SHA, временем и доказательством проверки.
  Различать «код опубликован», «код объединён» и «код установлен»: эти статусы не взаимозаменяемы.
- Перед выкатом сверить базу с реально установленным кодом и учесть чужие релизы. Если чужой патч отсутствует
  в ancestry ветки, проверить diff/эквивалентность и необходимые интеграционные проверки; не перезаписывать его
  устаревшим деревом. До появления release-state.json нужны явные проверки файлов/хешей и записи о выкатах.
- Патчноуты и Git помогают обнаруживать изменения, но не заменяют lock, STALE_BASE и проверку совместимости.
